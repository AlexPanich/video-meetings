# CLAUDE.md — apps/web

Фронтенд `video-meetings`: Next.js 16 (App Router), React 19, TypeScript. Общие правила репозитория — в корневом `CLAUDE.md`.

## Команды

Запускать из корня через `pnpm --filter web <script>` или из этой папки через `pnpm <script>`:

- `dev` / `build` / `start` — Next.js. `dev` и `start` запускаются с preload `scripts/disable-request-timeout.cjs` (`NODE_OPTIONS=--require …`): он снимает `requestTimeout` HTTP-сервера Node (по умолчанию 5 минут), которого Next не позволяет настроить, иначе загрузка файла до 500 МиБ на медленном канале обрывалась бы на прокси `/api/*`. Скрипты рассчитаны на POSIX-shell
- `lint` — ESLint (`eslint-config-next` + `eslint-config-prettier`)
- `typecheck` — `next typegen && tsc --noEmit`
- `test` — `vitest run`; `test:watch` — watch-режим

Один тест: `pnpm --filter web test src/app/page.test.tsx -t "renders main heading"`.

## Next.js 16

Версия с breaking changes: API, конвенции и структура файлов могут отличаться от привычных. Перед написанием кода читайте нужный гайд в `apps/web/node_modules/next/dist/docs/` и учитывайте deprecation-предупреждения. `next dev` сам создаёт `AGENTS.md` с этим правилом — это отключено через `agentRules: false` в `next.config.ts`.

## Структура

- `src/app/page.tsx` — главная (только для авторизованных: гость без cookie редиректится на `/login` в `src/proxy.ts` до рендера; внутри `<Suspense>` серверный `UserGreeting` через `getCurrentUser()` (`src/lib/server/auth.ts`, cookie → `GET /auth/me`) получает пользователя и при отказе API делает `redirect('/login')`, показывает `UserAvatar` (ссылка на `/profile`, `aria-label="Профиль"`) и приветствие; `MeetingsOverview` (счётчик встреч, последние 3, кнопка «Создать встречу» — пока заглушка без действия; данные из `getMeetings()` в `src/lib/server/meetings.ts`); `LogoutButton` — клиентский; оболочка страницы статична, данные пользователя динамические); `src/app/meetings/[id]` — страница встречи (только для авторизованных; `params` читается внутри `<Suspense>` в серверном `MeetingDetails`: данные встречи через `getMeeting()` — результат `{ ok, data } | { ok: false, status }`: 401 → `/login`, 404 (нет/чужая встреча, небезопасный id, ответ не той формы) → `notFound()`, прочее (5xx, сеть) → сообщение «Не удалось загрузить встречу», а не 404; ниже клиентский блок `MeetingFiles`: зона загрузки `FileUploader` (кнопка «Выбрать файлы» и drag-and-drop, несколько файлов за раз; каждый файл грузится независимо через `uploadFile()` из `src/lib/upload.ts` — обёртка над `XMLHttpRequest` с `upload.onprogress`, `FormData` с полем `file`, вне `request()` из `api.ts`; одновременно идут не больше 3 загрузок, остальные «В очереди»; у файла свой прогресс, статусы «Загружается»/«Загружен»/«Ошибка», кнопки «Отменить»/«Убрать»/«Повторить»; когда вся очередь завершилась, список перечитывается одним запросом и только потом загруженные файлы уходят из очереди; файл, брошенный мимо зоны, браузером не открывается, закрытие вкладки во время загрузки переспрашивается; файл больше 500 МиБ (`MAX_UPLOAD_BYTES`, как на API) не отправляется, показывается сообщение; при уходе со страницы загрузки прерываются и помечаются ошибкой — Next 16 страницу скрывает, а не размонтирует, состояние остаётся) и список файлов (у каждого файла — ссылка «Скачать» `<a download>` на `/api/meetings/:id/files/:fileId/download`, имя берётся из `Content-Disposition`, и кнопка «Удалить» (обе только у файлов `uploaded`) с подтверждением в `AlertDialog`: после `DELETE` файл убирается из списка и запоминается, чтобы запоздавший ответ списка его не вернул; фокус переходит на список; 404 считается успехом, 401 уводит на вход, прочие ошибки показываются в диалоге): имя, размер, дата, статус и состояния загрузки/пусто/ошибка с повтором; при 401 блок уводит на `/login`; форматирование — `src/lib/format.ts`, даты и время — клиентский `LocalDateTime` (в поясе зрителя, на сервере пустой `<time>`: сервер пояс не знает)); `src/app/(auth)/login`, `register` — страницы входа и регистрации (`AuthShell` + `LoginForm`/`RegisterForm` из `src/components`).
- `src/lib/api.ts` — клиент API (`login`, `register`, `getMe`, `updateProfileName` (`PATCH /api/profile`), `uploadAvatar`/`deleteAvatar` (`/api/profile/avatar`), `getMeetingFiles`, `meetingFilesPath`, `deleteMeetingFile`, `fileDownloadUrl`, `ApiError`, `logout`; загрузка файлов — отдельно в `src/lib/upload.ts`). Запросы идут на `/api/*` — это route handlers Next (BFF), CORS не нужен: `src/app/api/auth/{login,register,logout}` ставят/сбрасывают HttpOnly-cookie `access-token` (JWT от API в браузер не попадает, клиенту отдаётся только `user`), а `src/app/api/[...path]` проксирует остальное на бэкенд (`API_URL`, по умолчанию `http://localhost:3001`), подставляя `Authorization: Bearer` из cookie и сбрасывая cookie при 401. Прокси потоковый: тело запроса идёт в API как `request.body` с `duplex: 'half'` (без `arrayBuffer()`), `Content-Length` пробрасывается (API отсекает слишком большой файл заранее), из ответа передаются `Content-Type`, `Content-Disposition`, `Content-Length`, `Cache-Control`, `X-Content-Type-Options` — без них скачанный файл потерял бы имя и открывался бы inline. Через него идут файловые эндпоинты (`/api/meetings/:id/files…`: загрузка, список, скачивание, удаление). `src/proxy.ts` закрывает `/`, `/meetings/*` и `/profile/*`, но **не** `/api/*`: иначе Next буферизует тело запроса и загрузка больших файлов ломается. Серверные хелперы — `src/lib/server/auth.ts`.
- `src/app/profile/page.tsx` — профиль (только для авторизованных; серверный `Profile` в `<Suspense>` берёт `getCurrentUser()`, при отказе — `/login`; `ProfileCard` показывает `UserAvatar` (клиентский: при `hasAvatar` — `<img>` с `/api/profile/avatar?v=<avatarVersion>`, версия в URL меняет адрес при замене, а API отдаёт файл с `Cache-Control: private, max-age=31536000, immutable`, поэтому браузер не скачивает его повторно; при отсутствии аватара или ошибке загрузки — инициалы (в том числе если ошибка случилась до гидратации: `onError` её не увидит, поэтому при монтировании проверяются `complete` и `naturalWidth`): первая буква или цифра каждого из первых двух слов, знаки препинания пропускаются, без букв — «?»; тот же компонент на главной и `/profile/edit`), имя, email и ссылку «Редактировать» на `/profile/edit`); `src/app/profile/edit/page.tsx` — редактирование (только для авторизованных; серверный `EditProfile` в `<Suspense>` отдаёт клиентскому `AvatarEditor` аватар и клиентской форме `ProfileNameForm` текущее имя). `AvatarEditor`: выбор файла (скрытый `<input type="file">` с `aria-label="Выбрать изображение"`), проверка до отправки через `validateAvatarFile()` из `src/lib/avatar.ts` (JPEG/PNG/WebP, до 5 МБ — как `PUT /profile/avatar`; формат окончательно проверяет API), загрузка `uploadAvatar()` (`PUT /api/profile/avatar`, `FormData`, через `request()` из `api.ts`), удаление `deleteAvatar()` только после подтверждения в `AlertDialog` (404 — успех, прочие ошибки в диалоге); ошибки загрузки показываются в `Alert` с `role="alert"`, текущий аватар при них не меняется, ошибка сбрасывается при скрытии страницы и после удаления; 401 уводит на `/login` (при удалении диалог закрывается, чтобы не зависнуть); после успеха `router.refresh()` в `useTransition` обновляет `/profile` и главную, а кнопки остаются в состоянии `pending` до конца перехода; повторная отправка блокируется через ref; после удаления фокус возвращается на «Загрузить фото». Форма проверяет имя до отправки через `validateName()` из `src/lib/profile-name.ts` (те же правила, что `PATCH /profile` в API: не пусто после обрезки пробелов, до 100 символов — по символам, а не по единицам UTF-16, как считает class-validator, — без управляющих символов, с буквой или цифрой), ошибки API показывает в `Alert`, при 401 уводит на `/login`, держит `pending` (`useTransition`) до конца перехода, чтобы не отправить форму дважды, при скрытии страницы (Next 16 не размонтирует её) сбрасывает ввод и ошибку, а на странице получает `key` из id и имени пользователя; под полем всегда зарезервировано место под ошибку — иначе при потере фокуса кнопка «Сохранить» уезжает из-под курсора и клик теряется; после успеха делает `router.push('/profile')` и `router.refresh()` — Next 16 хранит открытые страницы, и без обновления профиль и главная показали бы прежнее имя.
- `src/app` — маршруты App Router (`layout.tsx`, `page.tsx`, `globals.css` с Tailwind и HeroUI).
- Алиас путей `@/*` → `src/*`.
- `next.config.ts` (rewrites больше нет) включает `cacheComponents` и `partialPrefetching` — учитывать при работе с кэшированием и динамическими данными в Server Components.

## Тесты

- Vitest, окружение jsdom, `globals: true` (`describe`/`it`/`expect` без импортов).
- `@testing-library/react`; jest-dom-матчеры подключены в `vitest.setup.ts`.
- Тесты лежат рядом с кодом: `src/**/*.{test,spec}.{ts,tsx}`.

## UI

HeroUI v3 (`@heroui/react`, `@heroui/styles`) на Tailwind CSS v4. Провайдер не нужен; стили подключены в `src/app/globals.css` (`@import 'tailwindcss'` → `@import '@heroui/styles'`, порядок важен), PostCSS — `postcss.config.mjs`. Компоненты составные (`Card.Header`), обработчики — `onPress`, не `onClick`. Перед добавлением компонентов сверяйтесь со скиллом `heroui-react` и документацией (`https://heroui.com/docs/react/components/<name>.mdx`).

## Особенности

- Dev-сервер на порту 3000; API слушает 3001, конфликта нет.
- `.next`, `next-env.d.ts` и `tsconfig.tsbuildinfo` — генерируемые файлы, не править вручную.
