# Plan: Загрузка файлов встречи

**PRD:** @docs/prd-meeting-file-upload.md
**Дата:** 2026-11-03

## Правило тестов (test-first)

В каждой фазе первой задачей пишутся тесты на поведение фазы, и их запускают до реализации: они должны быть **красными**. Затем реализуется фаза, и в конце те же тесты должны стать **зелёными**. Фаза не считается готовой, пока тесты, написанные в её начале, не позеленели.

- API-фазы (1–3): e2e-тесты в `apps/api/test/*.e2e-spec.ts` (`pnpm test:e2e`, реальная БД).
- UI-фазы (4–6): тесты web на Vitest + Testing Library (`pnpm --filter web test`). В проекте нет браузерного e2e-раннера, а его добавление не входит в PRD.

## Фазы реализации

### Фаза 1: Tracer Bullet — загрузка и список файлов (API)

**Цель:** Минимальный рабочий путь: владелец встречи загружает файл через API, файл попадает на диск и в БД со статусом `uploaded`, виден в списке.
**Затрагивает:** backend / database
**Задачи:**

- [ ] Написать e2e-тесты и убедиться, что они красные: загрузка нескольких файлов, список файлов встречи, 401 без токена, 404 для чужой встречи
- [ ] Модель Prisma для файла встречи (имя, размер, MIME-тип, дата, статус `uploading|uploaded|failed`, связь со встречей), миграция; переменная окружения каталога хранения с дефолтом в `.env.example`
- [ ] `POST /meetings/:id/files`: потоковая запись на диск (без загрузки в память) под сгенерированным именем, исходное имя только в БД; команда и handler по CQRS
- [ ] `GET /meetings/:id/files` (query и handler) с доступом только владельцу встречи (404 для чужой) и только авторизованным (401)
- [ ] Описание эндпоинтов в Swagger; e2e-тесты первой задачи зелёные

**Когда готова:** e2e-тесты, написанные в начале фазы, зелёные: через API можно загрузить несколько файлов в свою встречу и увидеть их в списке со статусом `uploaded`; 401/404 покрыты.

### Фаза 2: Лимит размера и обработка ошибок загрузки (API)

**Цель:** Загрузка устойчива к превышению лимита и обрывам, на диске не остаётся мусора.
**Затрагивает:** backend
**Задачи:**

- [ ] Написать e2e-тесты и убедиться, что они красные: 413 на файл больше 500 МБ, статус `failed` и отсутствие файла на диске после обрыва загрузки
- [ ] Лимит 500 МБ на сервере: ответ 413, частично записанный файл удаляется
- [ ] При обрыве соединения или ошибке записи запись получает статус `failed`, незавершённый файл удаляется с диска
- [ ] Unit-тесты handler'а загрузки (успех, превышение лимита, ошибка потока)
- [ ] Проверить, что загрузка файла в 500 МБ не увеличивает память процесса API на размер файла; e2e-тесты первой задачи зелёные

**Когда готова:** e2e-тесты, написанные в начале фазы, зелёные; прерванная загрузка даёт `failed` без файла на диске, память при большой загрузке не растёт на размер файла.

### Фаза 3: Скачивание и удаление файлов (API)

**Цель:** Полный жизненный цикл файла на стороне API.
**Затрагивает:** backend
**Задачи:**

- [ ] Написать e2e-тесты и убедиться, что они красные: побайтное совпадение скачанного файла и исходное имя, удаление (БД и диск), очистка файлов при удалении встречи, 401/404
- [ ] `GET /meetings/:id/files/:fileId/download`: потоковая отдача с исходным именем и MIME-типом
- [ ] `DELETE /meetings/:id/files/:fileId`: удаление записи из БД и файла с диска
- [ ] Удаление физических файлов с диска при удалении встречи
- [ ] Описание в Swagger, unit-тесты handlers; e2e-тесты первой задачи зелёные

**Когда готова:** e2e-тесты, написанные в начале фазы, зелёные: файл скачивается побайтно идентичным с исходным именем, после удаления файла или встречи на диске ничего не остаётся.

### Фаза 4: Прокси Next.js и список файлов на странице встречи (UI)

**Цель:** Пользователь видит файлы встречи в вебе, а прокси способен пропускать большие тела без буферизации.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать тесты UI и убедиться, что они красные: список с именем, размером, датой и статусом; состояния загрузки, пустого списка и ошибки
- [ ] Route handlers Next.js для файловых эндпоинтов (загрузка, список, скачивание, удаление): потоковое проксирование без буферизации до 500 МБ; JWT из HttpOnly-cookie
- [ ] Блок «Файлы» на странице встречи со списком файлов и их статусами
- [ ] Состояния списка: загрузка, пустой список, ошибка; тесты первой задачи зелёные

**Когда готова:** тесты, написанные в начале фазы, зелёные; на странице своей встречи отображается список файлов со статусами.

### Фаза 5: Зона загрузки с прогрессом (UI)

**Цель:** Пользователь загружает файлы из браузера и видит прогресс и статус каждого.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать тесты UI и убедиться, что они красные: выбор нескольких файлов, прогресс и статусы по каждому, отказ при файле больше 500 МБ, ошибка и повтор
- [ ] Зона загрузки на HeroUI: выбор кнопкой и drag-and-drop, несколько файлов за раз
- [ ] Отдельная загрузка каждого файла с собственным прогрессом и статусами «Загружается» / «Загружен»
- [ ] Проверка лимита 500 МБ на клиенте до отправки с понятным сообщением
- [ ] Статус «Ошибка» и кнопка повторной загрузки; тесты первой задачи зелёные

**Когда готова:** тесты, написанные в начале фазы, зелёные: несколько файлов грузятся независимо, файл больше 500 МБ не отправляется, после ошибки доступна повторная попытка.

### Фаза 6: Скачивание, удаление в UI и документация

**Цель:** Завершить пользовательский сценарий и привести документацию в актуальное состояние.
**Затрагивает:** frontend / документация
**Задачи:**

- [ ] Написать тесты UI и убедиться, что они красные: скачивание файла из списка, удаление с подтверждением и исчезновение из списка
- [ ] Кнопка скачивания (исходное имя) и кнопка удаления с подтверждением
- [ ] Обновить `CLAUDE.md`, `apps/api/CLAUDE.md` и `.env.example` (модуль файлов, эндпоинты, переменная каталога хранения, прокси)
- [ ] Финальная проверка: `pnpm lint`, `pnpm test`, `pnpm test:e2e` проходят; тесты первой задачи зелёные

**Когда готова:** тесты, написанные в начале фазы, зелёные; выполнены все критерии готовности из PRD, линт, unit- и e2e-тесты проходят, документация актуальна.
