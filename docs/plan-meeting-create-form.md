# Plan: Форма создания встречи

**PRD:** @docs/prd-meeting-create-form.md
**Дата:** 2026-11-18

## Правило тестов (test-first)

В каждой фазе первой задачей пишутся тесты на поведение фазы, и их запускают до реализации: они должны быть **красными**. Затем реализуется фаза, и в конце те же тесты должны стать **зелёными**. Фаза не считается готовой, пока эти тесты не позеленели и не проходят `pnpm lint`, `pnpm test`, `pnpm test:e2e` и `pnpm --filter web typecheck`.

- API-фаза (1): e2e-тесты в `apps/api/test/meetings.e2e-spec.ts` (реальная БД) и unit-тесты валидации и handler'а.
- UI-фазы (2–4): тесты web на Vitest + Testing Library. Браузерного e2e-раннера в проекте нет, его добавление не входит в PRD.

## Порядок и зависимости

Фаза 1 не зависит от UI. Фаза 2 — минимальный рабочий путь в интерфейсе: работает и на текущем API (он уже принимает `title`, `date`, `participants`). Фазы 3 и 4 опираются на окно из фазы 2 и не зависят друг от друга. После любой фазы приложение остаётся рабочим.

## Фазы реализации

### Фаза 1: Tracer Bullet — правила `POST /meetings` (API)

**Цель:** API не принимает встречу с некорректными названием, датой или участниками и сохраняет нормализованные данные; это основа для формы.
**Затрагивает:** backend
**Задачи:**

- [ ] Написать e2e-тесты и убедиться, что они красные: 400 с понятным сообщением для пустого названия, названия из пробелов, длиннее 200 символов (после обрезки) и с управляющими символами; для имени участника пустого, из пробелов, длиннее 100 символов и с управляющими символами; для 51 участника; для отсутствующей и не-ISO 8601 даты; прошедшая и будущая даты принимаются; пробелы по краям названия и имён обрезаются, повторы участников без учёта регистра убираются в сохранённой встрече (`GET /meetings/:id`); встреча без участников создаётся с пустым списком; встреча, записанная в БД в обход новых правил, по-прежнему отдаётся `GET /meetings` и `GET /meetings/:id`
- [ ] `CreateMeetingDto`: обрезка пробелов, длины 1–200 и 1–100, запрет управляющих символов, не больше 50 участников, дата ISO 8601; сообщения об ошибках на русском, понятные пользователю. Правила только на входе `POST /meetings`, чтение встреч их не проверяет
- [ ] Удаление повторов участников без учёта регистра (первое написание сохраняется) в `CreateMeetingHandler` или DTO; unit-тесты нормализации и handler'а
- [ ] Описать ограничения `POST /meetings` в Swagger (поля DTO, ответ 400), обновить `CLAUDE.md` и `apps/api/CLAUDE.md`; e2e-тесты первой задачи зелёные

**Когда готова:** Прямой запрос к `POST /meetings` с нарушением любого правила названия, участников или даты получает 400; сохранённая встреча содержит обрезанные название и имена без повторов; старые встречи открываются; ограничения видны в `/docs`.

### Фаза 2: Модальное окно создания встречи (UI)

**Цель:** Пользователь создаёт встречу с главной: название, дата, время — и сразу попадает на её страницу.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать тесты и убедиться, что они красные: кнопка «Создать встречу» открывает окно с полями «Название», «Дата», «Время»; дата и время по умолчанию — сегодня и ближайший следующий целый час (в том числе переход через полночь); выбранные 15:00 по времени браузера уходят в API как соответствующий момент в UTC; успех закрывает окно и ведёт на `/meetings/:id`; пустое название, из пробелов, длиннее 200 символов и с управляющими символами не отправляется, у поля ошибка
- [ ] Компонент окна на HeroUI v3 (`Modal`, поле названия, поля даты и времени): по умолчанию текущий день и следующий целый час, перевод из часового пояса браузера в ISO 8601 UTC, клиентская проверка названия по тем же правилам, что в API
- [ ] Клиентский метод создания встречи в `src/lib/api.ts` через BFF (`/api/meetings`), подключить окно к кнопке в `meetings-overview.tsx`; встреча создаётся с пустым списком участников
- [ ] После создания главная показывает актуальные счётчик и «Последние встречи» без ручной перезагрузки (учесть `cacheComponents` и скрытие страницы в Next 16); проверить, что страница встречи и главная показывают время 15:00 в локальном времени
- [ ] Обновить `apps/web/CLAUDE.md`; тесты первой задачи зелёные

**Когда готова:** С главной можно создать встречу без участников; браузер оказывается на `/meetings/:id` с введёнными названием, датой и временем; встреча на 15:00 показывается как 15:00 на странице встречи и на главной; после возврата на главную счётчик увеличен, встреча есть в «Последних встречах».

### Фаза 3: Ввод участников тегами (UI)

**Цель:** Пользователь добавляет участников встречи прямо в форме.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать тесты и убедиться, что они красные: Enter и запятая превращают имя в тег и очищают ввод; крестик и Backspace в пустом поле удаляют тег; повтор без учёта регистра и пробелов по краям тег не добавляет; имя длиннее 100 символов или с управляющими символами не добавляется, 51-й участник не добавляется — причина показывается; невписанное в тег имя попадает в участники при отправке; отправленные участники видны на странице созданной встречи
- [ ] Поле «Участники» на HeroUI v3 (теги): добавление по Enter и запятой, удаление крестиком и Backspace, проверка длины, управляющих символов, повторов и лимита 50 по тем же правилам, что в API. Повтор определяется тем же ключом, что `participantKey` в `apps/api/src/meetings/participants.ts`: `normalize('NFKC')` → удалить `\p{Cf}` → схлопнуть `[\s\p{Z}]+` в один пробел → `trim()` → `toUpperCase().toLowerCase()`; иначе форма покажет два тега (`Анна Петрова` и `Анна  Петрова` — с двумя пробелами), а API молча сохранит один. Длина имени — в кодовых точках (`[...name].length`), как в API
- [ ] Передача участников (включая невписанное в тег имя) в запрос создания; ошибки участников от API показываются пользователю
- [ ] Обновить `apps/web/CLAUDE.md`; тесты первой задачи зелёные

**Когда готова:** Участники вводятся и удаляются тегами, повторы и некорректные имена не добавляются с объяснением причины, созданная встреча содержит введённых участников.

### Фаза 4: Ошибки, отмена и доступность окна (UI)

**Цель:** Окно надёжно ведёт себя при ошибках, повторных нажатиях, отмене и истёкшей сессии и полностью управляется с клавиатуры.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать тесты и убедиться, что они красные: при ошибке API (4xx, 5xx, сеть недоступна) окно остаётся открытым, данные сохраняются, показывается сообщение (для 400 — причина из API); кнопка «Создать» заблокирована и показывает загрузку во время запроса, повторные нажатия дают один запрос; 401 ведёт на `/login`; «Отмена», Esc и клик вне окна закрывают его без запроса, при следующем открытии форма пустая (дата и время — снова значения по умолчанию); фокус при открытии внутри окна и возвращается на кнопку «Создать встречу» после закрытия
- [ ] Обработка ответов в окне: сообщение об ошибке, сохранение введённых данных, переход на `/login` при 401, как в остальных формах
- [ ] Блокировка «Создать» с индикатором загрузки на время запроса и защита от повторной отправки
- [ ] Сброс формы при закрытии любым способом; проверка фокуса и клавиатурного управления окном
- [ ] Обновить `apps/web/CLAUDE.md`; тесты первой задачи зелёные

**Когда готова:** Ошибка API не теряет введённые данные, частые нажатия создают одну встречу, истёкшая сессия ведёт на `/login`, закрытие окна сбрасывает форму, окно полностью управляется с клавиатуры; `pnpm lint`, `pnpm test` и `pnpm test:e2e` проходят.
