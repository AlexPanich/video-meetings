# Plan: Профиль пользователя

**PRD:** @docs/prd-user-profile.md
**Дата:** 2026-11-03

## Правило тестов (test-first)

В каждой фазе первой задачей пишутся тесты на поведение фазы, и их запускают до реализации: они должны быть **красными**. Затем реализуется фаза, и в конце те же тесты должны стать **зелёными**. Фаза не считается готовой, пока эти тесты не позеленели и не проходят `pnpm lint`, `pnpm test`, `pnpm test:e2e` и `pnpm --filter web typecheck`.

- API-фазы (1, 3, 5): e2e-тесты в `apps/api/test/*.e2e-spec.ts` (реальная БД) и unit-тесты handler'ов.
- UI-фазы (2, 4, 6): тесты web на Vitest + Testing Library. Браузерного e2e-раннера в проекте нет, его добавление не входит в PRD.

## Порядок и зависимости

API-фазы не зависят от UI и друг от друга. UI-фазы опираются на свою API-фазу, а фазы 4 и 6 — ещё и на страницы из фазы 2. После любой фазы приложение остаётся рабочим.

## Фазы реализации

### Фаза 1: Tracer Bullet — изменение имени (API)

**Цель:** Минимальный путь изменения профиля: пользователь меняет своё имя через API, и `GET /auth/me` сразу возвращает новое значение.
**Затрагивает:** backend
**Задачи:**

- [ ] Написать e2e-тесты и убедиться, что они красные: успешное изменение имени и новое значение в `GET /auth/me`, отказ для пустого имени и имени из пробелов, 401 без токена, изменение затрагивает только владельца токена, в ответе нет `passwordHash`
- [ ] Модуль `profile` и `PATCH /profile`: контроллер, DTO с обрезкой пробелов, команда и handler по CQRS. Пользователь определяется только по токену, для чтения профиля остаётся `GET /auth/me`
- [ ] Unit-тесты handler'а
- [ ] Описать эндпоинт в Swagger, обновить `CLAUDE.md` и `apps/api/CLAUDE.md`; e2e-тесты первой задачи зелёные

**Когда готова:** Через API можно изменить своё имя, новое значение видно в `GET /auth/me`; пустое имя, запрос без токена и утечка `passwordHash` покрыты тестами.

### Фаза 2: Страницы профиля и редактирование имени (UI)

**Цель:** Пользователь попадает в профиль с главной, видит свои данные и меняет имя.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать тесты и убедиться, что они красные: `/profile` показывает инициалы, имя и email; «Редактировать» ведёт на `/profile/edit`; блок приветствия содержит ссылку на `/profile`; форма показывает ошибку для пустого имени и имени из пробелов; `proxy.ts` уводит гостя с обеих страниц на `/login`
- [ ] Закрыть `/profile` и `/profile/edit` в `src/proxy.ts`, сделать страницу `/profile` и компонент аватара, который пока показывает инициалы
- [ ] Добавить компонент аватара со ссылкой на `/profile` в `UserGreeting`
- [ ] Сделать страницу `/profile/edit` с формой имени и клиентским методом в `src/lib/api.ts`: успех, ошибка валидации, переход на `/login` при 401. После сохранения `/profile` и главная показывают новое имя без ручной перезагрузки
- [ ] Обновить `apps/web/CLAUDE.md`; тесты первой задачи зелёные

**Когда готова:** Пользователь переходит с главной в профиль, открывает редактирование и меняет имя; новое имя видно на `/profile` и на главной без ручной перезагрузки, гость попадает на `/login`.

### Фаза 3: Загрузка, выдача и удаление аватара (API)

**Цель:** Полный жизненный цикл аватара на стороне API.
**Затрагивает:** backend / database
**Задачи:**

- [ ] Написать e2e-тесты и убедиться, что они красные: загрузка JPG, PNG и WebP, 413 для файла больше 5 МБ, отказ для SVG и файлов с подменённым расширением или MIME-типом (текущий аватар не меняется), прежний файл отсутствует на диске после замены и удаления, 401 без токена, 404 при выдаче и удалении без аватара, ответы без `passwordHash`
- [ ] Поля аватара в модели `User` (имя файла в хранилище, MIME-тип, версия или дата обновления) и миграция; признак наличия аватара и версия в `PublicUser`, чтобы браузер не показывал прежнее изображение из кэша
- [ ] `PUT /profile/avatar`: запись потоком через `receiveSingleFile` в `UPLOADS_DIR/avatars` под uuid-именем, лимит 5 МБ, проверка формата по сигнатуре файла. Порядок: записать новый файл, обновить БД, удалить старый; при ошибке новый файл удаляется, запись в БД остаётся прежней
- [ ] `GET /profile/avatar` и `DELETE /profile/avatar`: выдача только своего аватара с MIME-типом из БД и `X-Content-Type-Options: nosniff`; удаление сначала очищает запись в БД, затем удаляет файл. Unit-тесты handler'ов
- [ ] Описать эндпоинты в Swagger, обновить `CLAUDE.md` и `apps/api/CLAUDE.md`; e2e-тесты первой задачи зелёные

**Когда готова:** Через API можно загрузить, заменить, получить и удалить свой аватар; недопустимые файлы отклоняются без изменения текущего аватара, прежний файл не остаётся на диске.

### Фаза 4: Аватар в интерфейсе (UI)

**Цель:** Пользователь управляет аватаром на странице редактирования и видит его в профиле и на главной.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать тесты и убедиться, что они красные: компонент показывает изображение или инициалы; файл больше 5 МБ и файл другого формата не отправляются, причина показывается; ошибка API показывается, текущий аватар не меняется; удаление выполняется только после подтверждения
- [ ] Компонент аватара показывает изображение через `/api/profile/avatar` с версией в URL и инициалы при его отсутствии
- [ ] Блок аватара на `/profile/edit`: выбор файла, клиентская проверка формата и размера, загрузка и отображение ошибок
- [ ] Удаление аватара с подтверждением в `AlertDialog`. После загрузки и удаления `/profile` и главная показывают актуальное состояние без ручной перезагрузки
- [ ] Обновить `apps/web/CLAUDE.md`; тесты первой задачи зелёные

**Когда готова:** Загруженный аватар виден на `/profile`, `/profile/edit` и на главной, замена и удаление отражаются без ручной перезагрузки; после удаления показываются инициалы.

### Фаза 5: Смена пароля и завершение других сессий (API)

**Цель:** Пользователь меняет пароль через API, токены, выданные раньше, перестают действовать.
**Затрагивает:** backend / database
**Задачи:**

- [ ] Написать e2e-тесты и убедиться, что они красные: успешная смена и вход только с новым паролем; отказ для неверного текущего пароля, нового пароля короче 8 символов и совпадающего с текущим; прежний токен получает 401 на эндпоинтах профиля, встреч и файлов, новый токен работает; 401 без токена; смена не затрагивает других пользователей; ответ без `passwordHash`
- [ ] Поле `tokenVersion` в модели `User` и миграция (по умолчанию 0); версия в payload JWT из `TokenService`; токен без версии считается версией 0, чтобы действующие сессии не обрывались при выкатке
- [ ] `JwtAuthGuard` сверяет версию токена с БД и отвечает 401, если она не совпадает или пользователя нет; проверка выполняется до чтения тела запроса при загрузке файлов
- [ ] `PUT /profile/password`: команда и handler по CQRS, проверка текущего пароля, атомарное обновление хеша и версии, в ответе новый токен. Неверный текущий пароль возвращает **не** 401: иначе BFF сбросит cookie и разлогинит пользователя. Unit-тесты handler'а и guard'а
- [ ] Описать эндпоинт в Swagger, обновить `CLAUDE.md` и `apps/api/CLAUDE.md`; e2e-тесты первой задачи зелёные

**Когда готова:** После смены пароля вход работает только с новым паролем, прежние токены получают 401, а токен из ответа работает; ошибки валидации не меняют пароль.

### Фаза 6: Форма смены пароля (UI)

**Цель:** Пользователь меняет пароль на странице редактирования и остаётся в системе, другие его сессии уходят на вход.
**Затрагивает:** frontend
**Задачи:**

- [ ] Написать тесты и убедиться, что они красные: route handler кладёт новый токен в HttpOnly-cookie и не отдаёт его браузеру; форма показывает причину для неверного текущего пароля, короткого нового, совпадающего с текущим и расхождения с повтором; при расхождении запрос не отправляется; поля очищаются после успеха; 401 уводит на `/login`
- [ ] Отдельный route handler `src/app/api/profile/password/route.ts`: общий прокси `[...path]` не умеет ставить cookie, а без обновления cookie текущая сессия оборвётся
- [ ] Форма на `/profile/edit` на основе `PasswordField`: текущий пароль, новый пароль и повтор; клиентский метод в `src/lib/api.ts`
- [ ] Проверить, что сессия с прежним токеном при следующем запросе или переходе попадает на `/login`
- [ ] Обновить `apps/web/CLAUDE.md`; тесты первой задачи зелёные

**Когда готова:** После смены пароля текущая вкладка продолжает работать, сессия с прежним токеном попадает на `/login`, все ошибки показываются пользователю с причиной.
