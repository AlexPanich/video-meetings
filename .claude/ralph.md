# Ralph Loop - правила автономной работы

Одна итерация - одна Issue. Не берись за вторую: следующую возьмёт Stop Hook. Единственное исключение - раздел «Красные тесты следующих Issues» ниже.

## Как брать Issues

- Читай title, body и критерий готовности
- Бери открытую Issue с наименьшим номером из milestone, который указан в запросе
- Задачи фазы идут по порядку плана (`docs/plan-user-profile.md`): сначала красные тесты, потом реализация
- Проверяй что указанная ветка уже существует (если нет, создай от `main`: `git switch -c <ветка> main`; если есть - `git switch <ветка>`)
- Работай только в этой ветке - не создавай новых

## Именование коммитов

- По правилам в skill git-commit, сообщения на русском (см. корневой `CLAUDE.md`)
- Pre-commit запускает `pnpm lint` и `pnpm test`, коммит должен их проходить
- Единственное исключение для `--no-verify`: коммит красных тестов (первая задача фазы), у которого тип `test`. Только в такой форме, с флагом сразу после `commit`: `git commit --no-verify -m "test(<область>): <описание>"`. Остальные коммиты, включая реализацию, идут без `--no-verify`, и перед ними `pnpm lint` и тесты должны быть зелёными

## Красные тесты следующих Issues

Первая задача фазы коммитит красные тесты на всю фазу сразу. Поэтому pre-commit может быть красным не из-за твоей Issue, а из-за тестов следующих Issues той же фазы.

- Сначала убедись, что падают именно такие тесты: их имена и файлы относятся к открытым Issues этой фазы, а тесты твоей Issue зелёные
- Хук не обходи (`--no-verify` разрешён только для коммита красных тестов) и не останавливайся
- Не коммить и не закрывай Issue сразу: реализуй следующие Issues фазы по порядку в этой же итерации, пока `pnpm test` не станет зелёным
- Затем закоммить работу отдельными коммитами по задачам (`Refs #<номер>` в теле), перед каждым коммитом тесты должны быть зелёными; запушь ветку и закрой все сделанные Issues, в комментарии к каждой укажи коммит
- Если красные тесты не относятся к открытым Issues этой фазы, это настоящая поломка: действуй по правилу о пяти попытках ниже

## Правила реализации

- Сначала тесты - потом реализация (TDD)
- После каждого финального изменения запускай тесты: `pnpm test`, для API-фаз ещё `pnpm test:e2e`, для web ещё `pnpm --filter web typecheck`
- Не запускай dev-серверы (`pnpm dev` и подобные): они заняты у разработчика
- Если тесты красные после 5 попыток - остановись и напиши в Issue комментарий с описанием проблемы (`gh issue comment`), Issue не закрывай
- Если изменение меняет архитектуру, обнови документацию в том же коммите (см. раздел «Keeping docs up to date» в `CLAUDE.md`)

## Правила завершения

- Убедись что все тесты зелёные
- Убедись что все требования Issue и критерий готовности фазы выполнены
- Запусти skill /code-review для код ревью и исправь найденное
- Закоммить изменения и запушь ветку: `git push -u origin <ветка>` (без этого Stop Hook не сможет создать PR)
- Закрой Issue: `gh issue close <номер> --comment "<что сделано и в каком коммите>"`
- Не создавай PR это сделает Stop Hook
